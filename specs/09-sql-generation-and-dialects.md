# SQL generation, explanations and dialect specification

Requirements: [specification 01](01-requirements.md), R01, R03, R09, B02 and B06. Quality focus: SQL accuracy (25%).

## Generation behavior

Inputs are the current task, selected dialect, trusted schema/metrics and bounded conversation. Output must express the user's question faithfully with existing fields. Do not substitute a vaguely related query to force success. Return a clarification when the schema or request is insufficient. The SQL panel only receives a candidate after all validation and final optimization checks pass.

Use explicit projections for common examples and readable formatting with line breaks for clauses. SELECT * is allowed if schema-validated and requested, with an advisory about projected columns; do not treat readability preferences as hard SQL errors. Deterministic ordering is required when using top-N examples. A user-requested LIMIT is distinct from the independent execution cap. Do not silently insert a LIMIT into a query whose full aggregation the user requested; the runtime caps returned rows rather than altering aggregate inputs.

## Required example contracts

| Request | Meaning and acceptance |
| --- | --- |
| Show all employees hired after January 2024 | employees.hire_date >= '2024-01-01'; explanation explicitly states the specified inclusive January 1, 2024 boundary |
| Show all customers | Query only customers; full validated fields or explicit useful projection |
| Only those from California (after customers) | Preserve previous query and add customers.state = 'California'; no invented state code column |
| Show customers in California | Return only actual California rows; use actual state field |
| Monthly revenue for 2025 | orders ↔ order_items via FK; 2025 filter; month/year grouping; non-cancelled revenue; chronological sort |
| Top 5 products by revenue | products ↔ order_items ↔ orders through FKs; historical line value; descending revenue, deterministic tie break; LIMIT 5 |
| Employees by department | employees.department_id = departments.id; explain whether row listing or counts; clarify if unspecified |
| What are our best customers? | Ask what best means (revenue, orders or another metric) and period |
| Show customer phone numbers | Clarify that phone data is unavailable; do not invent phone |

Example tests compare semantics and real results, not fragile whitespace/string identity. Where multiple valid SQL forms exist, validate schema, predicates and expected result properties.

## Query constructs

Support safe SELECT projections, filters, ordering, grouping/HAVING, DISTINCT, aggregate/scalar functions, nonrecursive CTEs, scalar/IN/EXISTS subqueries, safe window functions and set operations where schema and joins can be validated. Reject constructs whose semantics cannot be checked under the declared restrictions. A limitation is preferable to accepting an unverified query. Unsupported output is not a successful query.

## Dialect matrix

Amendment A10 and [specification 18](18-dialects-follow-ups-and-setup.md) restore a compact output selector inside the query workspace. The prior SQLite-only UI amendment is superseded; native execution boundaries below remain unchanged.

| Concern | SQLite | PostgreSQL | MySQL |
| --- | --- | --- | --- |
| UI/API key | sqlite | postgres | mysql |
| Parse/render | SQLGlot SQLite | SQLGlot Postgres | SQLGlot MySQL |
| Identifier quoting | double quotes when needed | double quotes | backticks |
| Month formatting | strftime | TO_CHAR/date formatting as generated by translator | DATE_FORMAT |
| Limit | LIMIT | LIMIT | LIMIT |
| Execution in this app | Read-only SQLite | Validated transpilation to read-only SQLite | Validated transpilation to read-only SQLite |

Validate the selected dialect's AST and translated SQLite AST. Use SQLGlot's unsupported-operation error level so unsupported translations fail. SQLite compilation is required. The UI, API cost/result and downloaded SQL metadata identify the selected output dialect and SQLite execution engine. Changing dialect regenerates/translates from a known source dialect; do not parse old PostgreSQL output as MySQL without telling the server its origin. A pending or old turn retains its original dialect.

## Semantic boundaries

String case, collations, timezone behavior, integer division, NULL ordering, dates and dialect-specific functions can differ across engines. Document this; reject unsupported or lossy known translations rather than claim native cross-engine equivalence. Date strings use ISO format and examples avoid timezone-dependent expressions. Native PostgreSQL/MySQL execution, engine credentials and native optimizer costs are not implemented under this sample-database design. Multiple-dialect support does not mean arbitrary vendor extensions are accepted.

## Explanation contract

Every accepted SQL output has a plain-English explanation covering the data selected, key predicates and date bounds, joins/relationships, aggregates/grouping, sorting/limit and the meaning of any derived metric. Match the final optimized query. Avoid presenting raw SQL syntax as the entire explanation. Include assumptions in a separate visible list where relevant. Do not say results were fetched unless execution occurred. For executed queries report engine, row count, truncation and measured duration separately from the semantic explanation.

For debug, include original issue plus correction explanation. For optimization, describe actual rewrites separately from suggestions. When no safe rewrite exists, explicitly say only formatting/advice was applied. Do not claim an index was created or that a suggestion improved measured performance without evidence.

## Keyless sample mode

Supported deterministic intents: customer listing and state filtering; employee hire-date example; monthly 2025 revenue; top product revenue; counts on known business tables; supported follow-ups to an accepted query; safe pasted SELECT validation/formatting; obvious unambiguous misspelling repair. Recognize only documented patterns. Other requests clarify that full natural-language support needs server configuration. Never show a pretend model name or label canned templates as live AI.

## Acceptance

For all three dialects, parse formatted output, enforce table/column/FK checks, execute the SQLite translation and compare a stable set of result values for the reference queries. Assert explanations include actual filters and metric assumptions. Verify no-data queries succeed with zero rows and no fabricated data. Verify ambiguous/invented-schema requests return no SQL.
